Code over scale: an open-weights agent against the frontier

A post-mortem of building an agent for the BitGN ecom1 agentic-commerce benchmark — and what it taught me about agents.

2026-05 · Ruslan Kovalev executor: DeepSeek-V4-Pro (open-weights) best 88.6/100 · #6 of 100 on the public leaderboard

TL;DR

I built an agent for a 100-task "agentic commerce" benchmark and pushed it from 55 → 88.6 / 100 (#6 of 100 — top open-weights entry). The single biggest idea was "LLM as parser, code as compiler": let the capable, non-frontier open-weights model do the understanding, and move every deterministic step — grounding-reference assembly, policy lookup, math, file formatting, output validation — into ordinary Python. Most of the remaining work wasn't smarter prompts; it was schema design, error-recovery, and measurement discipline. I also bench-raced ~16 recent models through the same harness and learned that "which model is best" is meaningless without "on which harness."

1 · The challenge

BitGN ecom1 is an agentic-commerce benchmark. The agent operates a fake company's back-office as a file-shaped virtual machine: it can tree / find / search / read / write / delete / stat / exec, and finishes each task by calling report_completion(message, grounding_refs, outcome). There are 100 tasks, each scored 0 or 1 — one wrong action, one missing/extra reference, one wrong output token, or one mis-chosen outcome code, and the whole task is zero.

What the tasks test

  • Catalogue lookups — "does this exact product exist?" (typed attribute matching)
  • Availability counts — "how many of these N items ≥ K in stock today?"
  • Mutations — checkout, discount, 3-DS recovery, refunds (real state changes, with authority & policy checks)
  • Fraud detection — cluster shared-fingerprint / impossible-travel payments
  • Dispatch optimization — route packages over capacitated lanes
  • Exports — write a byte-exact TSV report
  • Security — refuse PII requests & prompt injection with the right refusal code

Why it's brutal

  • Production mode has no SQL — files + a minimal jq only.
  • Schemas vary by workspace — directory names and even the yes/no token (TRUE(1) vs ja/nein) differ per task.
  • Instances randomize every run — same task id, different data each trial, so you can't memorize and one run is noisy.
  • The grounding ref must be an exact record_path field — which differs from the file's on-disk path.
  • The executor isn't frontier. The open-weights track meant driving DeepSeek-V4-Pro (open-weights SOTA) in JSON mode — a capable model, but ~10 points behind frontier closed models at following this strict protocol on a fiddly harness. That gap shaped everything.

2 · How the best agent ended up looking

A small ReAct loop wrapped in a lot of deterministic scaffolding. The model proposes one step at a time as a typed JSON object; code does everything that doesn't need a model.

The three pillars

1. The completion compiler — "LLM as parser, code as compiler." The model never hand-writes the final reference set. It emits a family (e.g. discount) and subject_ids (bare entity IDs like basket-0003). Code resolves those to the exact record_path values the grader wants, attaches the policy documents that family requires, and runs a verifier with one repair turn. Grounding is assembled and tracked by code, never trusted from the model's memory.

2. Deterministic solvers (code owns selection & bytes). Fraud clustering, dispatch routing, byte-exact TSV rendering, and catalogue matching live in Python that the model calls from a sandbox. The catalogue matcher even discovers the schema at runtime (probes one product + one location to infer field names), so the same code works across the varying dev/prod layouts.

3. An evidence ledger + exact-byte I/O. The runtime records every path the agent observed, and vm_write lets a solver's exact output bytes hit disk without the model re-typing them (re-typing was silently corrupting TSV exports).

4 · Everything tried (including the dead ends)

kept  What worked

  • Completion compiler + verifier + one repair turn
  • Deterministic solvers (fraud, dispatch, crosslist, catalogue)
  • Self-discovering catalogue schema (no hardcoded field names)
  • Evidence ledger of observed paths
  • vm_write for exact-byte exports
  • Schema relaxation + self-correcting retry loop
  • Provider failover + per-call timeout
  • A 3-model "consensus" review of the design

cut  What backfired

  • Lean per-family prompts. The exact move a strong-model winner used. It regressed us 81→54 — the non-frontier executor needed more scaffolding, not less.
  • Prompt bloat. Piling rubrics on diluted the non-frontier JSON-mode model too.
  • Bundling fixes. Shipping 4 fixes at once hid an interaction that zeroed a whole run.
  • Aggressive grounding auto-add. Citing every file touched over-cites on an exact-set grader.
  • Whole-bucket fraud heuristics (over-flagged) — tuned down to endpoint-pairs.

5 · The model bake-off (and a trap)

With the harness fixed, I ran ~16 recent models (open- and closed-weight) through the same agent on a "hard set" — the tasks our best model still failed (so the set actually discriminates). A coercion shim wrapped each model's native tool-call shape into our schema so they could all drive the harness.

6 · Lessons about agents

Lesson 1 · architecture

LLM as parser, code as compiler.

The biggest lever by far. Split every task into understanding (the model is good at this — parse intent, locate records, decide an outcome) and assembly (it is bad at this — exact references, policy chains, math, byte-perfect files). Push all assembly into deterministic code. A stochastic model does deterministic work stochastically; you don't want a 95%-reliable string-formatter in a 0/1-graded pipeline.

Lesson 2 · grounding

Track state and evidence in code, not in the model's memory.

The model forgets paths, invents siblings, and over-/under-cites. The runtime should own an evidence ledger and build the answer's references from IDs the model names. Independently, every winner of this benchmark's sibling converged on the same thing: "the model reasons; the runtime tracks grounding and validates outcomes."

Lesson 3 · the executor sets the rules

A non-frontier model needs more scaffolding, not less — and there's a sweet spot.

The lean per-family prompt that a GPT-5-class agent thrived on regressed our open-weights model from 81 to 54. But piling on rubrics also diluted it. Scaffolding is model-dependent: frontier models want terse autonomy, models a notch below want explicit rails — and both have a bloat ceiling. Tune the amount of help to your executor.

Lesson 4 · the last mile

On a strict grader, precision beats intelligence.

Most of our zeros were "formally invalid but semantically almost-correct": a path missing a leading slash, a premature OUTCOME_OK, a sibling SKU variant, re-typed bytes. The model usually understood the task; it fumbled the contract. A deterministic compiler + verifier is how you stop losing points you've already earned.

Lesson 5 · failure modes

temperature=0 turns a transient error into a permanent one.

Six tasks silently produced no answer. Cause: the output schema required a non-empty "plan" list, but a finishing step legitimately has an empty plan → validation rejected it → and at temperature 0 the model reproduced the identical invalid JSON on every retry, so the loop gave up. Retrying an unchanged prompt at temp 0 is futile. Fix: relax the schema and make retries self-correcting — feed the validation error back so the input differs.

Lesson 6 · schema is design

Your output schema is a contract with the model and with your own code.

A too-strict constraint (min/max length on a list) silently killed answers. Then, after relaxing it, an unguarded plan[0] access started throwing on the now-legal empty list and zeroed an entire run. The schema sits between two consumers; loosen one side and you can break the other. Treat the schema as a first-class part of the agent.

Lesson 7 · measurement

Know your eval's noise floor before you trust a delta.

Randomized instances gave a per-run standard deviation of ≈4 points. A "+2-point improvement" from one run is noise. This changes strategy: raise the mean with high-coverage fixes, and — because the leaderboard takes your best run — exploit variance with best-of-N only after the mean has moved. Don't optimize against a number you can't measure.

Lesson 8 · change control

Fix one category at a time.

I once shipped four fixes in one run; an interaction between two of them zeroed the whole run, and I couldn't see which until I unbundled them. With a noisy 0/1 eval you lose causality fast. One change, one measurement, ideally on a targeted replay set of the failures you're attacking.

Lesson 9 · evaluation

"Best model" is meaningless without "on which harness."

A cheap open model tied the flagship on hard reasoning but lost badly on the full set, because our harness was tuned to one model's quirks. A model's benchmark rank is a property of the model × harness pair, not the model. And a discriminating "hard set" is great for ranking reasoning but can mislead about overall performance, which is dominated by the many easy tasks.

Lesson 10 · don't trust, enforce

Force tool use; make the exact bytes flow through code.

The model would call a perfect TSV-rendering solver and then re-type its output into the write tool, quietly changing the casing. The fix wasn't a better prompt — it was giving the sandbox a vm_write so the solver's exact bytes hit disk directly, plus a read-back check. If a step must be exact, don't route it through the model's keyboard.

Lesson 11 · cost

Agent cost is input-dominated; caching is a first-class lever.

25:1 input:output. The expense is the system prompt plus the ever-growing tool-output history replayed each step, not the model's short JSON replies. Prompt caching roughly halved the real cost. Design prompts and context windows with the input bill in mind, and keep stable prefixes cacheable.

Lesson 12 · portability

Cross-model portability needs a translation layer.

Models emit tool calls in different shapes; tool-tuned models especially love their own native format. A small coercion shim that maps any reasonable shape into your schema (wrap a flat {tool:…} into the NextStep envelope) is what let one harness drive a dozen models. Your schema is a lingua-franca you must be willing to translate to.

Blind spots & what we got lucky on

  • The architecture leaned on unusually inspectable state. The compiler strategy generalizes, but it was easy here because the world was file-shaped with explicit record_path values to cite.
  • A lucky constraint made us more robust. SQL being down in production forced file-native techniques — runtime schema discovery, jq, deterministic solvers, path ledgers. A SQL-dependent design would have been more brittle.
  • The score reflects best-of-N. With σ≈4 pts and a leaderboard that takes your best run, 88.6 is partly mean quality and partly variance sampling. Honest reporting separates the two.
  • The harness is model-tuned. Swapping models isn't an endpoint change — it's a re-tuning project (the bake-off proved it).
  • "One repair turn" is a double-edged safety valve. It rescued many near-misses, but a deeper loop might recover more — or cause new premature actions.

7 · What I'd do next

  • Push enforcement into the tool layer — make the answer impossible to submit unless a required solver "receipt" exists, and let code decide the security/clarification/unsupported outcome where it's deterministically knowable.
  • Trust-tagged reads — wrap file contents with provenance metadata so injected instructions inside data are structurally distinguishable from the real task.
  • A per-bucket replay harness — re-run only the failing category after each change, to beat the noise floor.
  • Best-of-N on a frozen config — since the board takes the best run and σ≈4 pts.

The one-sentence takeaway: a modest model wrapped in disciplined, deterministic code — that owns grounding, computation, formatting, validation, and error recovery — beats a smarter model left to do that work itself. Most of "agent engineering" is deciding what the model should not be trusted to do.
